# 09 · Database: models, constraints, migrations, indexes

> Phase 2 foundations. N+1 depth, soft deletion, auditing and
> zero-downtime migrations follow in Phase 7.

## Rules demonstrated

### 1. The database enforces the invariants too

Validation in code can be bypassed: by the shell, a data migration, another
service, or a bug. Each rule that must always hold is also a constraint:

| Rule | Constraint (both backends) |
|---|---|
| A title is never empty | `CHECK (title <> '')` |
| `status` is draft or published | `CHECK (status IN (...))` |
| published ⇔ `published_at` is set | `CHECK ((status='draft' AND published_at IS NULL) OR (status='published' AND published_at IS NOT NULL))` |
| One account per email, any case | unique index on `lower(email)` |

The constraints earned their place during Phase 2: when Schemathesis found a
validation gap (a `"\f"` title stripped to `""` *after* the length check), the
`CHECK` constraint refused the row. The bug surfaced as a 500 to fix,
not as silently corrupted data. See [36-api-contracts](../36-api-contracts/README.md#what-the-contract-tests-found).

Tests prove the constraints exist (`TestDatabaseConstraints`): writes that
bypass the services fail with `IntegrityError`.

### 2. UUIDv7 primary keys

Public IDs that can't be enumerated (`/posts/1`, `/posts/2`, ...), generated
without a database round trip. Version 7 starts with a millisecond timestamp,
so inserts append to the end of the index like auto-increment keys. Random v4
UUIDs scatter inserts across the whole B-tree. Python gets `uuid.uuid7` in
3.14; [`ids.py`](../../../django/reference_api/apps/core/ids.py) implements the RFC 9562 layout.

### 3. Every timestamp is `timestamptz`

SQLAlchemy maps `datetime` to `TIMESTAMP WITHOUT TIME ZONE` by default, and
naive timestamps are ambiguous across DST and servers. The FastAPI `Base`
maps all `datetime` columns to `timestamptz`. Django does this automatically
with `USE_TZ = True`. On the wire both emit RFC 3339 UTC (`...Z`), and a test
asserts the suffix.

### 4. Indexes match the queries

| Query | Index |
|---|---|
| public list: published, newest first, keyset | **partial** index on `(created_at DESC, id DESC) WHERE status = 'published'` |
| comments of a post, oldest first | `(post_id, created_at, id)` |
| login by email | unique index on `email` (values stored lowercased) |

A test runs `EXPLAIN` on the login query and fails on a sequential scan
([common problem](../../common-problems/case-insensitive-lookup-full-scan.md)).

### 5. Migrations

| | Django | FastAPI |
|---|---|---|
| Tool | `makemigrations` / `migrate` | Alembic (async template), URL from app settings, never from `alembic.ini` |
| Gate | `makemigrations --check` fails if models changed without a migration | `alembic check` fails if models and migrations differ |
| Tests | pytest-django builds the test DB from migrations | the session fixture runs `alembic upgrade head`, so the migrations themselves are tested |
| Naming | Django's built-in names | an explicit `naming_convention`, so constraints can be altered and dropped by name later |

Review autogenerated migrations. Functional and partial indexes and `CHECK`
constraints are where autogenerate is weakest.

**Set a custom user model before the first migration.** Phase 2 hit this for
real: the Phase 1 development database had been migrated with Django's
default `auth.User` and had to be recreated. On a production database this
is a multi-step data migration.

**Alembic gotcha:** `migrations/env.py` calls `logging.config.fileConfig()`,
whose default `disable_existing_loggers=True` silently disabled the app's
loggers whenever migrations ran in-process (tests, startup migration). It is
fixed in `env.py` and caught by a logging test.
